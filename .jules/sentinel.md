## 2025-02-14 - SSRF and DNS Rebinding vulnerability in register endpoint
**Vulnerability:** The `/api/ivc/register` endpoint validated user-provided host URLs against standard private/loopback IPs, but relied entirely on string matching of standard IP ranges (like `127.`). It was susceptible to octal/hex conversions, IPv4-mapped IPv6 formats (like `::ffff:127.0.0.1`), and most importantly, DNS rebinding. The vulnerability allowed an attacker to register a local host endpoint for the server to ping, compromising internal services by exposing `localhost` directly.
**Learning:** Checking for DNS resolution IP requires utilizing robust IP range checks like `ipaddr.js` rather than naive string prefixes to handle alternative address syntaxes correctly. Furthermore, checking the IP is useless if we still perform the request to the original hostname, since DNS can change immediately after validation.
**Prevention:** Always use a verified library (like `ipaddr.js`) to parse and validate IP address types. Mitigate DNS rebinding by explicitly forcing `fetch` or other HTTP clients to connect directly to the validated IP address instead of the hostname. When making a request to an IP, manually re-attach the original `Host` header to preserve SNI/virtual hosting where necessary.

## 2026-08-21 - Reserved Channel Spoofing via Slash Prefix
**Vulnerability:** The direct posting endpoint in `server.ts` (`app.post("/*")`) captures the channel name by removing a single leading slash (`req.path.substring(1)`). If an attacker submitted a post request to a path with multiple leading slashes (e.g., `//test`), `channelRaw` became `/test`. Because `/test` doesn't begin with protected characters like `+`, the post was allowed through. However, channels prefixed with `/` are unassigned but reserved for future functionality, which allowed a malicious user to squat or manipulate reserved channel names.
**Learning:** Always validate downstream parsed/derived resource names. Stripping a character is a mutation; if a route acts as a catch-all mapping to a namespace, it is critical to implement explicit boundaries/validation on the resulting namespace string (e.g. `channelRaw`).
**Prevention:** Implement a strict validation check directly after extracting the resource name to ensure it doesn't violate namespace constraints, such as explicitly rejecting any channel name that still begins with a reserved character like `/`.

## 2026-08-24 - Privilege Escalation via Malformed Mode Strings
**Vulnerability:** The application authorized users by splitting the `x-ivc-user` header on `+` and exclusively checking the second element (e.g., `ivcUser.split('+')[1].includes('a')`). An attacker could supply multiple `+` symbols in their mode string (e.g., `@user+user+a`), shifting their actual modes into index 2. This caused the application to evaluate `user` instead of `a`, resulting in broken privilege evaluation and allowing auth bypasses or privilege escalation.
**Learning:** String splitting on a delimiter (`+`) when the payload may contain multiple instances of the delimiter assumes a strict two-part format. When evaluating privilege strings (which represent sets of characters), the code must handle cases where the delimiter appears multiple times, especially when the identifier itself might contain the delimiter or if a secondary delimiter is used by an attacker to pad the string.
**Prevention:** Rather than using `.split('+')[1]`, use `.substring(ivcUser.indexOf('+') + 1)` to extract everything after the first `+` character. This ensures all mode assignments are captured and evaluated, regardless of how many `+` characters follow.

## 2026-08-24 - SSRF via HTTP Redirect Follow
**Vulnerability:** The application prevented SSRF by validating the provided `ivc_host` against local IP addresses and using the resolved IP to prevent DNS rebinding. However, the subsequent `fetch()` call to register the service omitted `redirect: "error"`. If the external server (which successfully bypassed IP checks) returned a 302 Redirect to a local IP address (e.g., `http://127.0.0.1/admin`), `fetch()` would automatically follow it, bypassing the application-level SSRF checks entirely.
**Learning:** Checking the initial requested IP is insufficient for SSRF protection because HTTP clients often follow redirects automatically. A seemingly safe external domain can easily redirect to an internal or restricted network endpoint.
**Prevention:** Always set `redirect: "error"` or `redirect: "manual"` when making HTTP requests (such as with `fetch()`) in SSRF-sensitive contexts. If redirects must be supported, each redirect URI must be recursively subjected to the same strict IP validation logic before being followed.

## 2024-05-30 - Prevent Identity Spoofing on Unauthenticated Channels
**Vulnerability:** Identity Spoofing on unprotected IVC standard channels (wildcard `app.post('/*')` routes).
**Learning:** The Zero-Trust Cryptographic Identity Engine (ZTCIE) middleware only intercepted requests starting with specific routing symbols (`+`, `-`, `#`, `@`, `$`, `§`, `∆`, `~`). For standard unauthenticated channels, the middleware was skipped, allowing attackers to directly set the `X-IVC-User` header and spoof any identity (e.g. `@admin+oa`).
**Prevention:** For wildcard routing and unauthenticated endpoints, explicitly reset claimed user identity headers (e.g. `req.headers['x-ivc-user'] = 'anonymous'`) if the request has not passed through the authentication middleware or if the path format implies it is unauthenticated.
